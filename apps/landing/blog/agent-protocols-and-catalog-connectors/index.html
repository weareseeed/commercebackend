Per-record API key salt

Agent API keys previously hashed against one shared, server-wide salt. New keys now use a per-record salt, generated at issuance and stored alongside a public apiKeyId that lets us look up the right salt before verifying the secret — without ever storing the secret itself. Keys issued before this change keep authenticating through the original shared-salt path; nothing was rotated or invalidated.

  • New key format: <prefix><16-hex keyId>.<secret>.
  • Verification is still scrypt-based; only the salting scheme changed.
  • Logger redaction was updated so the new salt field never appears in logs.

See docs/security.md for the full design.

Real ACP adapter

CommerceBackend now exposes a scoped, honestly-labeled subset of the Agentic Commerce Protocol (ACP) — the OpenAI/Stripe-authored spec — on top of our existing Stripe-hosted-checkout-redirect flow. Inbound and outbound mappers translate ACP's checkout-session shape to and from our native CheckoutIntent model, so no money-path code changed underneath it.

  • GET /v1/acp/product-feed — listings in ACP's product-feed shape.
  • POST /v1/acp/checkout-sessions — create a checkout session, mapped onto a CheckoutIntent.
  • GET /v1/acp/checkout-sessions/:id — read back session status.

This is not a claim of full or certified ACP spec compliance — see docs/api/protocol-acp.md for exactly which parts of the spec are and aren't implemented.

Real UCP adapter

Alongside ACP, we shipped our own vendor-neutral mapping layer we call UCP — a CommerceBackend-invented convention for framework portability, not a claim of conformance to any external standard with that name. It maps the same native checkout-intent model to a products / orders shape, including a full order-status mapping so agent frameworks built against it get consistent lifecycle states.

  • GET /v1/ucp/products
  • POST /v1/ucp/orders
  • GET /v1/ucp/orders/:id

Full mapping and status table in docs/api/protocol-ucp.md.

Read-only operator dashboard

A static, operator-key-gated dashboard (served at /operator/) gives a human operator visibility into agents, orders, and — as of this week — catalog sync activity, without adding any destructive controls. It reads through the same operator-only endpoints the API already exposes.

Square catalog connector spike

This week's largest piece of work is a read-only spike, not a production connector. There is no live Square API call anywhere in it — it reads a static fixture standing in for a Square "List Catalog" response, maps each catalog object onto CommerceBackend's canonical catalog-item shape, and writes ordinary Listing rows from it. No Square credentials exist anywhere in this repository.

What it doesHow
Maps Square-shaped catalog items A typed CanonicalCatalogItem shape, meant to be reused by future connectors (Shopify, BigCommerce, WooCommerce).
Imports without duplicating Listings are keyed on (importSource, externalId), so re-running a sync updates the same rows instead of creating new ones.
Tracks every sync A CatalogSyncLog row records items imported, items failed, and why — per sync run.
Isolates bad items One malformed catalog item (e.g. missing a price) is logged and skipped; it does not abort the rest of the batch.
Stays inside existing surfaces Imported listings show up through the unchanged /v1/search and /v1/listings/:id endpoints — no new agent-facing capability was added.

Both endpoints require an operator key, not a buyer/seller agent's bearer key:

POST /v1/connectors/square/sync
  X-Operator-Key: <operator key>
  { "sellerAgentId": "agent_seller_123" }

GET /v1/connectors/sync-logs?limit=20&offset=0
  X-Operator-Key: <operator key>
What this spike does not do: no live Square OAuth or Catalog API client, one-way only (nothing is ever written back to Square), no scheduled/automatic or webhook-driven re-sync, no diffing or partial-field merge on re-sync (last-write-wins), and no Shopify/BigCommerce/WooCommerce connectors yet — those remain separate, unstarted roadmap items.

Full endpoint reference in docs/api/connectors-square.md.

What none of this changes

The money path is untouched. Stripe test-mode checkout, webhook-backed order reconciliation, and every other money-path route from previous releases work exactly as before. Nothing in this recap touches production settings, credentials, or the money path.
